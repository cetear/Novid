# 日志记录与问题排查

更新日期：2026-10-10。

## 配置与文件

正式 API 使用 Spring Boot 管理的 Log4j 2（当前依赖树为 2.24.3），业务通过 SLF4J 写日志。公共 Boot starter 排除 `spring-boot-starter-logging`，避免 Logback 和 `log4j-to-slf4j` 与 Log4j 的 SLF4J 实现同时存在。contract 的异常脱敏辅助类保持纯 Java。CLI 使用 Log4j 2 默认控制台配置，正式文件配置属于 lab-app。

主配置在 `lab-app/src/main/resources/application.yml`，输出规则在同目录 `log4j2-spring.xml`。修改后重启生效；`.env.example`、Java 环境文件加载器及 `scripts/start-api.ps1` 均支持以下六项。已有 `.env` 无需补齐即可使用默认值。

| application.yml 参数 | 环境变量／.env | 默认值 | 用途 |
|---|---|---|---|
| logging.file.path | LOG_PATH | ./var/logs | 日志目录，自动创建；相对路径以进程工作目录为基准 |
| logging.level.root | LOG_LEVEL | INFO | 框架日志级别 |
| logging.level.com.example.ailab | LAB_LOG_LEVEL | INFO | 业务日志级别，排查可暂设 DEBUG |
| logging.log4j2.max-file-size | LOG_MAX_FILE_SIZE | 20MB | 单文件大小滚动阈值 |
| logging.log4j2.max-history-days | LOG_MAX_HISTORY_DAYS | 30 | 压缩归档保留天数 |
| logging.log4j2.max-archive-size | LOG_MAX_ARCHIVE_SIZE | 1GB | 两类压缩归档的累计大小阈值 |

使用正数大小和天数，日志目录需有写权限。Windows 示例：`LOG_PATH=D:/AICodeProject/Novid/var/logs`，无需引号。也可直接启动覆盖：

```powershell
java -jar lab-app/target/lab-app-0.1.0-SNAPSHOT.jar --logging.file.path=D:/NovidLogs --logging.level.com.example.ailab=DEBUG
```

- `novid.log`：业务和框架运行日志，默认 INFO 及以上。
- `novid-error.log`：ERROR 汇总，同一 ERROR 同时出现在主文件。
- `archive/novid-日期-序号.log.gz`、`archive/novid-error-日期-序号.log.gz`：按 UTC 日期或大小滚动压缩；每类每日最多 100 个序号。时间／总大小清理在主日志滚动时触发，只匹配本目录的 `novid-*.log.gz`。阈值不包含两个活动文件，也不是实时磁盘硬配额；无新日志时不会自行清理。
- 控制台同步输出；日志编码为 UTF-8，时间为 UTC（中国本地时间加八小时）。`var/`、`*.log` 和 `*.log.gz` 已被 Git 忽略。

## 功能覆盖与关联

正式 Spring 装配通过 `OperationLoggingAspect` 覆盖所有 `*ApplicationService` 公共入口：账户、知识库／文档、会话／问答、偏好／审批、任务／成果／执行图、费用／治理及媒体功能。记录 `operation.start`、`operation.complete` 或 `operation.failed`，包含操作名、结果、耗时及安全身份／资源编号。Spring 代理外的手工 new 对象和同类内部调用不重复记录入口；CLI 不装配此切面。

模型 chat／结构输出／工具续轮／embedding、媒体提交／查询、工具执行、文档入库流水线及治理维护也记录边界。模型每次实际尝试单独记录逻辑模型 ID、次数、结果、提供方用量和 Mock 标志，可看见主失败后备用成功。工具和媒体返回自身状态。

模型 `model.attempt_failed` 在默认 WARN 日志中保留脱敏异常类型及调用位置，删除原异常消息和 suppressed 内容。模型调用内的数据库校验异常归为 INTERNAL_ERROR，不当作模型输出错误或供应商连接故障触发付费重试；同步接口映射 HTTP 500，retryable=false。连接池相邻警告仍需结合异常链确认，不能仅凭时间相近认定根因。

媒体计划拒绝额外记录固定 `reason`，例如 `PLAN_CONTENT_DEPENDENCY`、`PLAN_ROLE`、`PLAN_JSON_UNKNOWN_FIELD`、`PLAN_CYCLE`。原 `MODEL_STRUCTURED_INVALID` 错误码及一次结构修复上限保持不变；不回显模型提交的字段值或 Jackson 原始消息。

资料结构拒绝的 `model.structured_invalid` 记录 schema、reason 及程序字段路径；异常诊断给出实际长度／数量、上限和单位，区分 UTF-8 字节、UTF-16 长度与项数。同一回答最多列出 32 项问题，不把未知字段名或模型正文写入诊断。视频单位也保留具体字段和原字符上限。模型结构纠正固定实际产出目标，语义／跨题／数量纠正使用保存的原模型身份；每次调用及校验在运行图中分别记录，仍受 max-nodes 和 payload 捕获上限约束。窗口容不下整份失败回答时，`model.repair_input draftIncluded=false draftBytes=...` 或纠正输入中的 `DRAFT_OMITTED_FOR_CONTEXT` 明确说明草稿未完整回送；原参数与诊断仍保留。生成节点缺少模型回执视为状态损坏，返回 `WORKFLOW_STATE_CONFLICT`，一次纠正用尽返回 `MODEL_REPAIR_EXHAUSTED`。V24 清理升级前的三类内容任务，不保留旧节点兼容。

报告和媒体 Worker 单次领取创建独立 `traceId`／`operationId`／`taskId`，记录开始、发布／等待审批／失败和执行退出；`worker.finished` 仅代表本次运行退出。入库、索引清理和续租异常有错误码及 ID；空队列扫描不写 INFO。

HTTP 外层过滤器覆盖成功请求和认证拒绝，记录方法、服务端匹配的路由模板、HTTP 状态、耗时。为每个请求生成 UUID，通过 `X-Request-Id` 响应头返回，忽略客户端同名头；未匹配路由记录 `UNMAPPED`。SSE 在实际异步完成时记录结束，超时／断线另有事件；工作线程显式传递并恢复 MDC，避免串号。模型和工具通过执行预算补上运行图 `traceId`、任务或入库 ID。

日志不展开参数／查询串／认证头／密码／token／配置凭证／用户正文／模型完整响应／媒体链接。预期业务拒绝为 WARN 和稳定错误码；意外异常为 ERROR，保留异常类型、最多八层原因链及每层最多 64 个调用位置，删除原异常消息和 suppressed 内容。SDK 详细日志关闭。日志不替代数据库权限审计、可靠任务事实及费用账本。

## 排查流程

1. 保存失败响应的 `X-Request-Id`，在主日志按 `requestId` 找请求、业务及 SSE 事件。
2. 后台任务按 `taskId`，文档处理按 `ingestionId`／`documentId` 查询；模型事件按 `traceId` 与运行图关联。
3. 检查 `code`、HTTP `status`、`durationMs` 和 `model.attempt_complete`，区分权限／版本冲突、排队、提供方失败和持久化故障。
4. 意外失败查 `novid-error.log`；需要模型底层调用位置时将 `LAB_LOG_LEVEL=DEBUG`，重启复现后恢复 INFO。不要开启 SDK 原始 HTTP DEBUG。
5. 未生成文件时核对进程工作目录、配置覆盖、目录权限及控制台 Log4j 配置诊断。正式服务需重新构建和重启才会生效。

接入方式参照 [Spring Boot 日志文档](https://docs.spring.io/spring-boot/reference/features/logging.html)、[Log4j 安装说明](https://logging.apache.org/log4j/2.x/manual/installation.html) 和 [滚动文件说明](https://logging.apache.org/log4j/2.x/manual/appenders/rolling-file.html)。本轮验证结果见[测试验证与验收报告](temp/测试验证与验收报告.md)。

## 固定资料工作流结构拒绝诊断（2026-10-10）

固定资料工作流新增 `event=model.structured_invalid schema=Facts reason=...`，日志继续带当前线程的运行关联字段。`JSON_FIELDS` 表示必填/额外字段集合不符，`JSON_TYPE` 表示类型或 null 不符，`JSON_SYNTAX` 表示 JSON 解析失败；提取阶段可进一步区分 `FACT_ID`、`FACT_SOURCE`、`FACT_QUOTE`、`FACT_COUNT`、`FACT_STATUS`、`FACT_TEXT_SIZE`。原因只来自服务端枚举，未知模型字段与内容不进入日志或修复消息。

出现结构失败后的并行 `REQUEST_CANCELLED` 时，先查同 traceId 中最早的结构拒绝。运行尝试数汇总所有并行工作包和修复，不能直接理解为单次调用的重试次数。历史失败响应未保存时，笼统的 MODEL_STRUCTURED_INVALID 不能推断具体字段原因；新诊断需要使用修复后的服务重跑才能产生。

私人模型文本快照解析 JSON 时也拒绝重复字段和尾随内容；解析失败则保留脱敏文本，避免把多个对象裁为第一个对象或覆盖重复字段，抹掉 `JSON_SYNTAX` 的证据。正常 JSON 仍按结构脱敏和格式化，捕获权限与长度上限保持原规则。历史快照可能已丢失这些语法信息，`truncated=false` 只表示保存阶段未截断，不能证明历史模型原文完整；不能从历史格式化快照逆推出具体的语法错误。

提取引用经一次结构修复后仍失败时，后端允许缩小该来源分片，记录 `event=content.extract_split sourceId=... offset=... bytes=... reason=FACT_QUOTE`；容量导致的拆分使用 `reason=CAPACITY`。只记录服务端来源标识及数字，不展开正文。分片缩小到不超过 500 UTF-8 字节仍拒绝时保留原引用错误。AGENT 节点异常现在也记录 FAILED 和 errorCode，既有运行图页面无需改接口即可展示；历史错误状态不回写。
