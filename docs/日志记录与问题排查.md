# 日志记录与问题排查

## 数据库连接竞争（2026-10-14）

新增日志只记录服务端入口名称、资源数量、耗时与稳定错误码，不输出SQL、数据库地址、凭证或正文：

- `db.pool_wait`：采样发现idle=0且waiting>0，记录active／idle／total／waiting／maximum；没有该日志不能证明采样间隔内未发生短暂满池。
- `db.content_slow`：资料仓库请求累计超过1秒，分别记录admissionMs及operationMs；后者包含获取连接、事务、SQL和应用计算，不能直接称为SQL耗时或锁等待耗时。
- `db.content_admission_timeout`：尚未进入资料仓库事务就等待许可超时；与连接池获取超时分开诊断。
- `task.renew_unavailable`／`task.renew_recovered`：续租事务开始阶段临时连接故障及后续恢复次数；recovered的valid=false仍表示执行权已失效，不能继续提交。
- `task.renew_deferred`／`learning.deferred`：有限续租恢复耗尽，当前执行退出，保留既有租约恢复机制；运行图中的本次执行失败不等同于父任务已写入FAILED。
- `learning.lease_lost`：心跳返回续租失败；前台提交仍独立核验执行权。
- `learning.failure_write_failed`／`content.package_failure_write_failed`：数据库连失败状态也无法保存，记录脱敏异常链和原错误码，不能把没有状态更新解释为任务成功。

Actuator已接入的连接池指标用于观察获取耗时、借出时长和等待数量；当前HTTP管理端点仍仅暴露health。必要时在诊断环境通过DB_LEAK_DETECTION_MS启用超长借出告警，告警仅是可能泄漏或长事务的线索。持续竞争时由有权运维账号采集JVM线程、innodb_trx及data_lock_waits，并关联阻塞者、等待者、事务开始时间和连接持有调用栈；应用账号缺少PROCESS时不自行改权限。数据库当前存活或事后Sleep连接不能还原历史故障。部署参数与恢复限制见[部署配置与运行维护](部署配置与运行维护.md)。

## 摘要超限的局部压缩（2026-10-13）

资料整编和学习自测的总摘要 `summary`、阅读包 `fragments[].topics[].summary` 与主题卡 `topics[].summary` 仅因文字长度超限时，纠正调用只发送超限摘要及对应标题、条件、关系等只读上下文，模型返回 `replacements`，程序合回原对象并执行完整业务校验。其他字段保持原值。摘要按原始 UTF-8 字节上限压缩，例如总摘要为 1800 字节；原有 50% 验收容差不成为压缩目标。替换值在服务端继承原字段的实际验收上限：宽松摘要允许至 2700 字节，严格摘要仍为 1800 字节。内部验收值仅用于校验和诊断，不进入局部压缩请求，避免把生成上限误当成另一套内部拒绝阈值。

局部压缩前扫描全部可压缩摘要，再通过本地完整核验排除其他错误，不能仅依赖最多 32 项的诊断列表。单次最多压缩 32 个摘要；混合错误、非摘要文字、原文引用、题目、数组数量、整个对象容量及语法错误继续采用原有完整纠正。局部请求放不进窗口时明确失败，不省略目标摘要。

首次调用仍登记原业务 Schema，局部压缩调用的 operation 为 `local-summary-compression`、Schema 为 `LocalSummaryCompression$Replacements`，全文为真实字段替换响应。`assembled_summary` 为本地 VALIDATION 节点，不能将其结果解释为另一份提供方响应或额外付费调用。合成失败只记录规则和位置，不留正文摘录副本。压缩共享原模型与一次纠正额度；无效替换不再追加整包重生成，费用按每次实际提供方用量结算。完整成功结果继续保存到原业务检查点与生成回执，恢复时按原业务 Schema 校验。

范围、测试证据及真实模型验证限制见[局部压缩实施记录](temp/资料整编与学习自测局部压缩实施记录-2026-10-13.md)。

## 调用校验与全文登记（2026-10-13）

资料整编和学习自测新 MODEL 节点同时保存响应状态与本地校验状态。打开 `/run-inspector.html`，选择本人运行和失败节点，查看具体规则、完整路径、期望、实际类型及失败摘录；可展开该业务节点的全部模型尝试，并分页查看／下载各次实际请求与响应。完整登记独立于图队列，图缺失时可使用“查看本次已登记调用”入口。旧运行不补录。

日志仍只保存字段、规则和数量；摘录和正文属于私有排错登记，不进入日志、公共异常、纠正诊断提示或OTLP。提供方调用成功但结构失败时，节点 FAILED、调用 SUCCESS、校验 FAILED；这不表示费用未发生。归档失败为 SAVE_FAILED，不重新调用模型。输入、输出分别处理存储异常，一侧描述查询或初始化失败不阻止另一侧保存；模型文本索引失败时可改看已完整保存的原始响应。WRITING、INCOMPLETE、EXPIRED、ACCESS_REVOKED 与历史 NOT_CAPTURED 分别说明写入中、响应未收完、过期、来源已撤销、没有登记。归档到期同步隐藏调用详情与节点副本的正文预览、快照和失败摘录，即使清理尚未物理删除记录也不能继续读取这些内容。

调用登记及正文引用中的日期在数据库 JSON 中使用 ISO 时间字符串，避免 MySQL 将数字日期保存为浮点数而丢失纳秒精度，导致完成归档时误判调用身份变化。历史数字日期仍可读取，但已经损失的精度和未登记的终态不会自动恢复。若调用列表残留 RUNNING／NOT_SENT，同时运行图和日志已经失败，应核对 `model.call_archive_failed`；调用列表不能单独证明模型仍在处理。

现行接口见[前端接口说明](前端接口与联调说明.md)，容量、保留期与迁移见[部署维护说明](部署配置与运行维护.md)，本次验证见[实施记录](temp/资料整编与学习自测调用校验及全文登记实施记录-2026-10-13.md)。旧快照规则继续用于未接入的其他工作流。

## 配置与文件

正式 API 使用 Spring Boot 管理的 Log4j 2（当前依赖树为 2.24.3），业务通过 SLF4J 写日志。公共 Boot starter 排除 `spring-boot-starter-logging`，避免 Logback 和 `log4j-to-slf4j` 与 Log4j 的 SLF4J 实现同时存在。contract 的异常脱敏辅助类保持纯 Java。CLI 使用 Log4j 2 默认控制台配置，正式文件配置属于 lab-app。

主配置在 `lab-app/src/main/resources/application.yml`，输出规则在同目录 `log4j2-spring.xml`。修改后重启生效；`.env.example`、Java 环境文件加载器及 `scripts/start-api.ps1` 均支持以下六项。已有 `.env` 无需补齐即可使用默认值。

| application.yml 参数 | 环境变量／.env | 默认值 | 用途 |
|---|---|---|---|
| logging.file.path | LOG_PATH | ./var/logs | 日志目录，自动创建；相对路径以进程工作目录为基准 |
| logging.level.root | LOG_LEVEL | INFO | 框架日志级别 |
| logging.level.com.example.ailab | LAB_LOG_LEVEL | INFO | 业务日志级别，排查可暂设 DEBUG |
| logging.log4j2.max-file-size | LOG_MAX_FILE_SIZE | 20MB | 单文件大小滚动阈值 |
| logging.log4j2.max-history-days | LOG_MAX_HISTORY_DAYS | 30 | 压缩归档保留天数 |
| logging.log4j2.max-archive-size | LOG_MAX_ARCHIVE_SIZE | 1GB | 两类压缩归档的累计大小阈值 |

使用正数大小和天数，日志目录需有写权限。Windows 示例：`LOG_PATH=D:/AICodeProject/Novid/var/logs`，无需引号。也可直接启动覆盖：

```powershell
java -jar lab-app/target/lab-app-0.1.0-SNAPSHOT.jar --logging.file.path=D:/NovidLogs --logging.level.com.example.ailab=DEBUG
```

- `novid.log`：业务和框架运行日志，默认 INFO 及以上。
- `novid-error.log`：ERROR 汇总，同一 ERROR 同时出现在主文件。
- `archive/novid-日期-序号.log.gz`、`archive/novid-error-日期-序号.log.gz`：按 UTC 日期或大小滚动压缩；每类每日最多 100 个序号。时间／总大小清理在主日志滚动时触发，只匹配本目录的 `novid-*.log.gz`。阈值不包含两个活动文件，也不是实时磁盘硬配额；无新日志时不会自行清理。
- 控制台同步输出；日志编码为 UTF-8，时间为 UTC（中国本地时间加八小时）。`var/`、`*.log` 和 `*.log.gz` 已被 Git 忽略。

## 功能覆盖与关联

正式 Spring 装配通过 `OperationLoggingAspect` 覆盖所有 `*ApplicationService` 公共入口：账户、知识库／文档、会话／问答、偏好／审批、任务／成果／执行图、费用／治理及媒体功能。记录 `operation.start`、`operation.complete` 或 `operation.failed`，包含操作名、结果、耗时及安全身份／资源编号。Spring 代理外的手工 new 对象和同类内部调用不重复记录入口；CLI 不装配此切面。

模型 chat／结构输出／工具续轮／embedding、媒体提交／查询、工具执行、文档入库流水线及治理维护也记录边界。模型每次实际尝试单独记录逻辑模型 ID、次数、结果、提供方用量和 Mock 标志，可看见主失败后备用成功。工具和媒体返回自身状态。

模型 `model.attempt_failed` 在默认 WARN 日志中保留脱敏异常类型及调用位置，删除原异常消息和 suppressed 内容。模型调用内的数据库校验异常归为 INTERNAL_ERROR，不当作模型输出错误或供应商连接故障触发付费重试；同步接口映射 HTTP 500，retryable=false。连接池相邻警告仍需结合异常链确认，不能仅凭时间相近认定根因。

媒体计划拒绝额外记录固定 `reason`，例如 `PLAN_CONTENT_DEPENDENCY`、`PLAN_ROLE`、`PLAN_JSON_UNKNOWN_FIELD`、`PLAN_CYCLE`。原 `MODEL_STRUCTURED_INVALID` 错误码及一次结构修复上限保持不变；不回显模型提交的字段值或 Jackson 原始消息。

`model.structured_invalid` 的默认 WARN 日志同时记录 `violations`：每项包含程序字段路径、违规规则及 `actual`／`maximum`／`unit`。`NON_BLANK` 表示空白，`MAXIMUM` 表示超出对应单位的上限；UTF-8 字节不等于字符数，启用工作流文字容差时 `MAXIMUM.maximum` 为实际验收上限。日志不包含模型正文、未知字段值或诊断的 `expected` 文本；即使运行图已达到节点或快照容量上限，仍可从此警告核对违规类型和数值。历史日志不会因此补齐，缺少详细诊断时不得仅凭输出 token 数断定字段超长。

业务校验可能通过 `RecordSchema.require` 收集违规后立即抛出结构失败。若该异常没有自带诊断，`RecordSchema.validate` 会保留已收集的规则和路径，供日志、私人节点详情及纠正提示使用；不能用空诊断的笼统错误覆盖实际证据。联合规划的 `sections[0].itemIds／NON_EMPTY` 表示主要事实清单为空，`sections／MISSING_COVERAGE` 表示主要小节未覆盖全部输入事实。已有明确诊断及权限、预算等其他错误仍原样传递；没有收集到证据时不补造诊断。50%文字容差不改变事实身份、唯一归属或完整覆盖要求。

整编分批复核后的协调节点会将 `COVERAGE_MISMATCH` 与程序元数据核对：只有全部源事实具有唯一主要归属，且该单元的冻结规划、`units.itemIds` 和 `coverage.available/selected` 完全一致时，报告元数据覆盖不一致才会被判为 `issues[n].evidence／CONTENT_CONSTRAINT`，交给已有的一次同模型结构纠正。纠正提示给出实际条目数量，禁止按编号连续性臆造事实；正文遗漏仍按 `MISSING_KNOWLEDGE` 等语义问题正常处理，不因元数据完整而视为正文正确。无法证明元数据一致时不屏蔽模型意见，纠正后仍违规则失败，不自动接受或增加纠正次数。排查 `WORKFLOW_REVIEW_REJECTED` 时应分别核对分批正文复核、局部修复和最终协调响应，不能把较早已恢复的格式或网络失败当成最终原因。

当前 `RecordSchema.schema()` 发送的原生结构定义约束必填字段、字段类型及额外字段；UTF-8 字节限制放在 `description` 与模型提示中，并由后端再次校验。`strict=true` 不代表这些描述性要求也成为结构定义的硬限制。`Summary.summary` 生成要求为 1800 UTF-8 字节，启用 50% 字段文字容差时验收上限为 2700 字节；JSON 合法且提供方返回成功，摘要仍可能超限。定位时核对实际请求中的规则、纠正诊断和归档响应的字节数，不能把字节超限归为 JSON 语法错误，也不能未经业务依据扩大上限或截断正文。

生成和纠正提示始终使用字段声明的原始上限：`summary.maximum=1800`。纠正提示会把具体数组下标对应到原字段规则，再用原始上限生成发给模型的诊断副本；内部 50% 容差不作为模型的生成目标。原异常、日志与私人校验诊断仍保存实际验收上限 2700，不能据此推断新的纠正请求也发送了 2700。历史请求全文保留当时的原始提示，不回写；新行为在重新构建并重启后应用于新调用。

资料结构拒绝的 `model.structured_invalid` 记录 schema、reason 及程序字段路径；异常诊断给出实际长度／数量、上限和单位，区分 UTF-8 字节、UTF-16 长度与项数。同一回答最多列出 32 项问题，不把未知字段名或模型正文写入诊断。视频单位也保留具体字段和原字符上限。模型结构纠正固定实际产出目标，语义／跨题／数量纠正使用保存的原模型身份；每次调用及校验在运行图中分别记录，仍受 max-nodes 和 payload 捕获上限约束。窗口容不下整份失败回答时，`model.repair_input draftIncluded=false draftBytes=...` 或纠正输入中的 `DRAFT_OMITTED_FOR_CONTEXT` 明确说明草稿未完整回送；原参数与诊断仍保留。生成节点缺少模型回执视为状态损坏，返回 `WORKFLOW_STATE_CONFLICT`，一次纠正用尽返回 `MODEL_REPAIR_EXHAUSTED`。V24 清理升级前的三类内容任务，不保留旧节点兼容。

报告和媒体 Worker 单次领取创建独立 `traceId`／`operationId`／`taskId`，记录开始、发布／等待审批／失败和执行退出；`worker.finished` 仅代表本次运行退出。入库、索引清理和续租异常有错误码及 ID；空队列扫描不写 INFO。

HTTP 外层过滤器覆盖成功请求和认证拒绝，记录方法、服务端匹配的路由模板、HTTP 状态、耗时。为每个请求生成 UUID，通过 `X-Request-Id` 响应头返回，忽略客户端同名头；未匹配路由记录 `UNMAPPED`。SSE 在实际异步完成时记录结束，超时／断线另有事件；工作线程显式传递并恢复 MDC，避免串号。模型和工具通过执行预算补上运行图 `traceId`、任务或入库 ID。

日志不展开参数／查询串／认证头／密码／token／配置凭证／用户正文／模型完整响应／媒体链接。预期业务拒绝为 WARN 和稳定错误码；意外异常为 ERROR，保留异常类型、最多八层原因链及每层最多 64 个调用位置，删除原异常消息和 suppressed 内容。SDK 详细日志关闭。日志不替代数据库权限审计、可靠任务事实及费用账本。

## 排查流程

1. 保存失败响应的 `X-Request-Id`，在主日志按 `requestId` 找请求、业务及 SSE 事件。
2. 后台任务按 `taskId`，文档处理按 `ingestionId`／`documentId` 查询；模型事件按 `traceId` 与运行图关联。
3. 检查 `code`、HTTP `status`、`durationMs` 和 `model.attempt_complete`，区分权限／版本冲突、排队、提供方失败和持久化故障。
4. 意外失败查 `novid-error.log`；需要模型底层调用位置时将 `LAB_LOG_LEVEL=DEBUG`，重启复现后恢复 INFO。不要开启 SDK 原始 HTTP DEBUG。
5. 未生成文件时核对进程工作目录、配置覆盖、目录权限及控制台 Log4j 配置诊断。正式服务需重新构建和重启才会生效。

接入方式参照 [Spring Boot 日志文档](https://docs.spring.io/spring-boot/reference/features/logging.html)、[Log4j 安装说明](https://logging.apache.org/log4j/2.x/manual/installation.html) 和 [滚动文件说明](https://logging.apache.org/log4j/2.x/manual/appenders/rolling-file.html)。本轮验证结果见[测试验证与验收报告](temp/测试验证与验收报告.md)。

## 固定资料工作流结构拒绝诊断（2026-10-10）

资料阅读新增 `event=content.read_phase`（2026-10-12）：`phase=MODEL_READING` 为全部阅读包完成耗时；`phase=CHECKPOINTS` 每 100 个片段及最终完成时记录派生检查点累计耗时和 `completedFragments`；`phase=READING_PROOF` 为全文证明及 prepare／extract 完成耗时。阶段采用单调时钟，只输出数量与耗时，按 `taskId`／`traceId` 关联。失败未完成的阶段结合最后进度与失败日志分析，未打印完成记录不表示耗时为零。测量及验证限制见[资料整编性能记录](temp/资料整编工作流性能分析与优化记录-2026-10-12.md)。

`MODEL_READING` 包含已有阅读包的恢复与核验，不能凭阶段名认定发生了模型请求；结合 MODEL 节点和请求日志判断。500K／64K 新默认策略下，整编事实数超过 32 时采用每批最多 64 条的容量自适应归并，较小的保存策略仍为超过 64 条时每批最多 32 条。`event=content.normalize_batch` 记录 `completedFacts`、`facts`、`batches`、`inputBytes` 和累计 `durationMs`，用于判断组织阶段实际进度及串行批次耗时。模型窗口不足或输出截断时拆小批次，不记录事实正文。

归并缩小至单条仍遇到模型容量错误时，`event=content.normalize_fallback` 记录进度和容量错误码，当前会话切换为逐事实的候选批量比较，避免对剩余每条事实反复探测不可用的批量协议。该回退可能增加请求数，需结合请求日志重新评估两小时目标。

固定资料工作流新增 `event=model.structured_invalid schema=Facts reason=...`，日志继续带当前线程的运行关联字段。`JSON_FIELDS` 表示必填/额外字段集合不符，`JSON_TYPE` 表示类型或 null 不符，`JSON_SYNTAX` 表示 JSON 解析失败；提取阶段可进一步区分 `FACT_ID`、`FACT_SOURCE`、`FACT_QUOTE`、`FACT_COUNT`、`FACT_STATUS`、`FACT_TEXT_SIZE`。原因只来自服务端枚举，未知模型字段与内容不进入日志或修复消息。

出现结构失败后的并行 `REQUEST_CANCELLED` 时，先查同 traceId 中最早的结构拒绝。运行尝试数汇总所有并行工作包和修复，不能直接理解为单次调用的重试次数。历史失败响应未保存时，笼统的 MODEL_STRUCTURED_INVALID 不能推断具体字段原因；新诊断需要使用修复后的服务重跑才能产生。

输入输出快照仅保存内容文本：正常 JSON 提取正文、摘要、问题、答案等值，剔除字段名与结构外壳、编号、哈希、资源策略、模型用量和协议定义；SDK 消息提取实际文本，不保存消息对象的字符串外壳。没有模型响应时不把失败诊断伪装成输出，错误码和状态保留在节点元数据，具体原因查关联日志。原捕获权限、脱敏与长度上限不变，历史快照不回写。

私人快照解析 JSON 时仍拒绝重复字段和尾随对象；无法解析的响应保留脱敏原始文本，以便排查语法失败。内容快照不是完整请求／响应 JSON，不能作为精确重放依据。`truncated=false` 只表示提取后的内容未截断，不能证明模型原文完整。

资料工作流的模型结果解析已容忍 Markdown JSON 围栏、额外字段及最多 50% 的字段文本超长；整体容量、数组数量和来源／覆盖规则仍有效。严格模式仍用于其他调用。整编省略逐片和逐章模型复核，格式、组织和重复类问题不阻止发布；全局及冲突验收仍处理实质错误。源信息核验在会话内共享 30 秒结果，prepare 完成与发布前强制刷新。

提取引用经一次结构修复后仍失败时，后端允许缩小该来源分片，记录 `event=content.extract_split sourceId=... offset=... bytes=... reason=FACT_QUOTE`；容量导致的拆分使用 `reason=CAPACITY`。只记录服务端来源标识及数字，不展开正文。分片缩小到不超过 500 UTF-8 字节仍拒绝时保留原引用错误。AGENT 节点异常现在也记录 FAILED 和 errorCode，既有运行图页面无需改接口即可展示；历史错误状态不回写。
